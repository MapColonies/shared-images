## Problem Statement

The `shared-images` monorepo contains multiple Dockerfiles representing both internally developed applications and extended third-party base images. Historically, managing nested folder structures, differing lifecycles, and varied versioning requirements caused pipeline bloat and release ambiguity. Furthermore, the lack of automated code quality checks (linting/formatting) and inconsistent commit messages disrupted automated changelog generation and monorepo health, making it difficult to track what changed in a specific component.

## Solution

We will implement a unified CI/CD architecture using GitHub Actions with a fully flat repository structure. Every service, application, or extended base image will reside in its own dedicated directory directly at the repository root. All images will be managed and versioned identically using Google's `release-please` for Conventional Commits-driven Semantic Versioning. This provides automated changelogs, a standardized release cadence, and complete structural uniformity across the monorepo. To maintain health and ensure the automated releases trigger correctly, we will enforce strict Conventional Commit messaging via Husky pre-commit hooks and root-level Prettier/linting checks on Pull Requests.

## User Stories

1. As a DevOps engineer, I want a flat repository structure where every service sits directly at the root, so that CI/CD path-filtering and matrix generation scripts are maximally simplified.
2. As a DevOps engineer, I want all images managed by a single `release-please` strategy, so that CI/CD logic is unified and easy to maintain.
3. As a software developer, I want all image versions and changelogs generated automatically based on my Conventional Commits, so I don't have to manually track releases or write changelogs.
4. As a developer, I want my local commit messages intercepted and validated by Husky, so that I am immediately notified if my message format is invalid before pushing.
5. As a release manager, I want every commit to explicitly declare its scope (the specific root-directory name or `global`), so that release changelogs accurately reflect exactly which service was modified.
6. As an infrastructure maintainer, I want upstream base image updates (e.g., bumping an extended Grafana image) explicitly stated in the commit message and injected as an OCI label, so that I can easily identify the underlying third-party version despite the semantic tag.
7. As a developer, I want a CI job to automatically run root-level linting and formatting checks on my Pull Requests, so that code quality and styling remain consistent across the monorepo.
8. As a platform architect, I want the deployment plan and configuration strictly configured to never generate release candidate (RC) tags, so that our registry only contains stable, finalized image artifacts ready for deployment.
9. As a developer, I want older versions of configuration files to be completely ignored during this pipeline execution, so that legacy CI behaviors do not interfere with the new architecture.

## Implementation Decisions

- **Flat Repository Structure:** All services and images will be moved to individual directories at the root level (e.g., `/my-internal-app/`, `/grafana-custom/`). 
- **Unified Release Pipeline (`release-please`):**
  - We will implement `google-github-actions/release-please-action` to handle versioning for the entire repository.
  - The configuration will map the release outputs to the Docker build/push steps uniformly for all root directories.
  - The pipeline configuration must be explicitly set to standard releases only; all references to release candidate (RC) tags are strictly removed from the deployment flow.
- **Commit Linting (Husky & Commitlint):**
  - Install `husky` and `@commitlint/cli` at the root.
  - A `commit-msg` Husky hook will be configured.
  - A custom rule in `commitlint.config.js` will enforce a unified `scope-enum`. The allowed scopes will be dynamically generated by reading all valid root-level directories (explicitly filtering out structural folders like `.github`, `node_modules`, or `.husky`), plus the `global` keyword.
- **Pull Request Quality Gate:**
  - A workflow (`.github/workflows/pr-checks.yml`) will execute `on: pull_request`.
  - It will run root-level `lint` and `prettier` checks. Passing this workflow is mandatory for merging.
- **Upstream Versioning Mitigation (For Extended Images):**
  - Images that extend third-party software will include standard OCI labels (e.g., `LABEL org.opencontainers.image.version="<UPSTREAM_VERSION>"`) in their Dockerfiles so infrastructure tools can query the base version independently of the internal semantic Docker tag.
- **Legacy Configuration Handling:**
  - Any older versions of CI/CD configuration files must be explicitly ignored or deleted during the implementation PR to ensure a clean slate.

## Out of Scope

- Deployment or continuous delivery (CD) of the generated images to Kubernetes, Docker Swarm, or other runtimes. This PRD covers only the Continuous Integration (CI), building, and registry publishing phases.
- Runtime vulnerability scanning of the images (e.g., using Trivy or Snyk).
- Migrating legacy image tags to the new semantic versioning convention.

## Further Notes

- Ensure that the GitHub Actions runners have sufficient caching configured for Docker layers, as monorepo builds can become slow if base layers are not cached efficiently.
- Root-level configuration files for the linter (`.eslintrc.js` or similar) and Prettier (`.prettierrc`) must be established prior to enabling the PR check blocking rule.
- The `commitlint` dynamic scope resolution script must be robust enough to handle the addition of new root directories automatically without requiring manual updates to the configuration file.
